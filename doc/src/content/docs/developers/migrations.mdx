Atomic CRM uses [declarative database schemas](https://supabase.com/docs/guides/local-development/declarative-database-schemas) to manage its database structure. The schema is defined in `.sql` files under `supabase/schemas/`, and migrations are auto-generated from those files.

## Schema Files

The `supabase/schemas/` directory contains the **source of truth** for the database structure:

        font-size: 1rem;
        display: table;
        width: 100%;
    }
    `}
</style>

| File               | Contents                                                                      |
| ------------------ | ----------------------------------------------------------------------------- |
| `01_tables.sql`    | Tables, foreign keys, indexes, extensions                                     |
| `02_functions.sql` | All PL/pgSQL functions                                                        |
| `03_views.sql`     | Views (`contacts_summary`, `companies_summary`, `activity_log`, `init_state`) |
| `04_triggers.sql`  | All triggers (public tables + auth.users)                                     |
| `05_policies.sql`  | Row Level Security policies                                                   |
| `06_grants.sql`    | Grants and default privileges                                                 |
| `07_storage.sql`   | Storage bucket policies                                                       |

Files are numbered to control load order (tables must exist before functions that reference them).

:::caution
Migration files in `supabase/migrations/` are auto-generated from the schema files. In most cases, you should not edit them directly. However, there are exceptions: for example, `db diff` may generate a DROP + CREATE for a column rename instead of an ALTER TABLE RENAME. In such cases, manually edit the migration to use the correct statement, while keeping it coherent with the schema files.
:::

## Working With a Local Database

When developing locally with `make start`, Supabase runs a local PostgreSQL instance. There are two ways to make schema changes locally.

### Option A: Edit Schema Files

1. **Edit the relevant schema file** in `supabase/schemas/`. For example, to add a column to the `contacts` table, edit `01_tables.sql`.

2. **Generate a migration** from your changes:

```sh
npx supabase db diff --local -f <migration_name>
```

This compares the schema files against the local database and generates a migration file in `supabase/migrations/`.

3. **Review the generated migration** in `supabase/migrations/`. In most cases it will be correct, but sometimes you may need to adjust it. For example, if you renamed a column, `db diff` may generate a DROP + CREATE instead of an `ALTER TABLE ... RENAME COLUMN`. Edit the migration file to use the correct statement, while keeping it coherent with the schema file.

4. **Apply the migration** locally:

```sh
npx supabase migration up --local
```

5. **Verify** the diff is clean (no remaining differences):

```sh
npx supabase db diff --local
```

This should output "No schema changes found".

:::danger[The column-order trap]
If step 5 instead prints `drop view` + `create or replace view` for views you
never touched, **do not generate a migration from it**. That output is
non-convergent: applying it does not change anything the diff is complaining
about, so the very next diff reproduces it identically — and each generated
`create view` silently loses `with (security_invoker = on)` and the grants
declared in `06_grants.sql`, which is an RLS bypass.

The real cause is a `create table` block in `01_tables.sql` whose column order
no longer matches the database. `alter table ... add column` always appends to
the tail and `drop column` leaves a hole, so a migration that removes a column
from mid-table and adds new ones puts the two out of step; `migra` compares
columns by ordinal position, decides the table changed, cannot express a
reorder in SQL, and emits only the collateral view drops.

Fix it by reordering the `create table` block in `supabase/schemas/01_tables.sql`
to match `pg_attribute.attnum` — a schema-file edit, never a migration:

```sh
npm run test:unit:db -- column_order   # names any table whose declared order has drifted
```

Then re-run `db diff` twice: once to see it clean, once to prove it converges.
See the `COLUMN-ORDER TRAP` header in `supabase/schemas/01_tables.sql`.
:::

:::danger[The empty-table trap]
Step 4 above applies your migration to a database that `db reset` just
rebuilt from nothing, and step 5 compares _shapes_. **Neither one can see a
row.** A migration that drops a column, renames a table or rewrites a derived
value is therefore perfectly green locally and still destroys production,
because production is the only place the table is not empty.

This has happened twice here. `20260729095558_backfill_member_state.sql`
shipped correct DDL with no backfill for pre-existing rows and blanked
production — HTTP 200 with zero rows on every surface.
`20260730011428_shidduch_overview_fields.sql` was caught at pre-flight: it
dropped `shidduchim.parents_en`/`parents_he` before adding
`father_*`/`mother_*`, with nothing in between, against 24 populated rows —
and its own review fix (`update public.shidduchim set id = id`, added to stop
`identity_signals.parents_norm` going stale) would have run _after_ the drop
and overwritten all 24 rows' `parents_norm` with NULL. Six clean `db diff`
runs saw none of it.

**Before `supabase db push`, run the guard:**

```sh
make check-migration-safety            # add STACK_ID=<n> for your own stack
```

It resets a local stack to the **last deployed** migration, seeds
production-shaped rows, applies only the _pending_ migrations, and then
asserts that every seeded row still exists, that every value in a surviving
column is unchanged, and that every column that disappeared while holding
data has a declared, _verified_ destination. CI runs the same script
(`🧬 Migration data-safety`) against the merge base.

When it goes red, the fix is almost always the same three moves inside the
migration file: **put the `add column`s above the `drop column`s, backfill
between them, and make it fail closed** — assert the data landed before the
drop runs, so a wrong assumption halts the deploy instead of erasing rows.
`db diff` will never emit any of that; it is a manual adjustment, and one of
the legitimate reasons to hand-edit a generated migration.

If a column's data genuinely goes nowhere, declare it in
`supabase/tests/migration-data-safety/declared-moves.sql` with a written
reason. That file is the guard's only per-migration input, and an undeclared
drop of a populated column is a failure by default.
:::

### Option B: Use Supabase Studio

You can modify the schema using the local Supabase Dashboard (Studio) at http://localhost:54323/. When working on a local database, Studio automatically creates a migration for each change you make.

After making your changes in Studio, update the relevant schema files in `supabase/schemas/` to match, so they remain the source of truth. You can inspect the current state with:

```sh
npx supabase db dump --local --schema public
```

## Working With a Remote Database

To apply schema changes to the remote (hosted) Supabase database, push the migrations generated locally:

```sh
npx supabase db push
```

This applies any pending migrations from `supabase/migrations/` to the remote database.

If you make schema changes directly on the remote database via the hosted Supabase Studio, those changes won't be reflected in the local schema files or migration history. To re-sync, pull the remote schema and update your local files:

```sh
npx supabase db pull
```

This generates a new migration matching the remote state. Then update the relevant schema files in `supabase/schemas/` to match.

## Editing Functions

Function definitions in `02_functions.sql` must use the exact format that PostgreSQL stores internally (quoted identifiers, specific indentation). Otherwise, `db diff` will show phantom changes on every run.

After editing a function, if `db diff` shows an unexpected `CREATE OR REPLACE FUNCTION` in its output, run:

```sh
npx supabase db dump --local --schema public
```

Then copy the function's exact format from the dump output into `02_functions.sql`.

## Updating The Import Feature

From the frontend UI, users can import contacts and companies via a csv file.

If you change the data structure for a contact, don't forget to modify the sample CSV file located at [`src/components/atomic-crm/contacts/contacts_export.csv`](https://github.com/marmelab/atomic-crm/blob/main/src/components/atomic-crm/contacts/contacts_export.csv). You'll also need to modify the import function found in [`src/components/atomic-crm/contacts/useContactImport.tsx`](https://github.com/marmelab/atomic-crm/blob/main/src/components/atomic-crm/contacts/useContactImport.tsx).
