## Overview

This runbook covers **handling a purge request submitted via the public page** (`/purge-request`). A purge request comes from a person who was suggested as a single in someone's account, never signed up, found out they are in the system, and wants their record removed. They have no account and no way to know which family holds them.

The first ten requests will be handled manually by a person, not an automated function. This runbook is for that person.

### Architecture Summary

| Component | Role |
|-----------|------|
| `PurgeRequestPage.tsx` | Public unauthenticated page — inserts one row into `purge_requests` |
| `public.purge_requests` | Table holding requests; `status` = `pending` → `verified` → `processed` |
| `public.verify_purge_request(text)` | RPC called by `PurgeRequestVerifyPage` — marks request `verified` |
| `PurgeRequestVerifyPage.tsx` | Page where requester clicks the emailed token to verify ownership |
| Admin review (this runbook) | Human process: identity check → locate records → notify accounts → delete per policy → record outcome |

## How a Request Arrives

1. Visitor lands on `/purge-request` (no auth required).
2. They fill in: their name, an email or phone to reach them, and optional free-text details.
3. On submit, a row is inserted into `purge_requests` with:
   - `single_name` — what they typed
   - `contact` — email or phone
   - `details` — free text (may contain school, community, shadchan name, years)
   - `status = 'pending'`
   - `verification_token` — generated by a `BEFORE INSERT` trigger (not yet in DB; another agent owns the database half)
   - `expires_at = now() + 7 days`
4. An email is sent to `contact` with a link to `/purge-request/verify?token=<verification_token>`.
5. Requester clicks the link → `PurgeRequestVerifyPage` calls `verify_purge_request(token)` → row becomes `status = 'verified', verified_at = now()`.
6. **Admin (you) sees a verified request ready for review.**

> **UNVERIFIED:** The email-sending mechanism (trigger? edge function? cron?) is owned by another agent. I have not read that code. If no email arrives, the request stays `pending` and expires after 7 days. Check with the database agent before assuming the email path works.

## Establishing Identity Proportionately

The requester has no account. They cannot prove "I am Chaya Cohen" cryptographically. The verification token only proves "someone with access to this email/phone clicked the link." That is the **only** identity signal we have.

**Do not ask for:** government ID, selfie, notarized letter, or any credential the requester cannot reasonably produce.

**Do:** treat the verified token + the details they provided as a **lead**, not proof. Your job is to see whether the lead points to a real record in our system.

### Identity Check Steps

1. Open the verified `purge_requests` row (status = `verified`, `verified_at` not null).
2. Read `single_name`, `contact`, `details`.
3. Search `singles` for rows matching `single_name` (exact or fuzzy).
4. Cross-reference `details`:
   - School / seminary / yeshiva name
   - Community / location
   - Approximate age / birth year
   - Shadchan name mentioned
   - Years they were suggested
5. If **exactly one** `singles` row matches all provided signals → proceed.
6. If **zero** rows match → record "no match found" in `purge_requests.result`, set `status = 'processed'`, notify requester (if contact is email), close.
7. If **multiple** rows match → **do not guess**. Record "ambiguous match" in `result`, set `status = 'processed'`, notify requester asking for more detail, close.
8. If the matched `single` belongs to an account where the requester **is** a member (they actually have an account) → this is not a purge-request case; redirect to account deletion (Story 14.2). Record in `result`, close.

> **UNVERIFIED:** There is no admin UI for browsing `purge_requests` yet. You will likely query `public.purge_requests` directly in Supabase SQL Editor. Ask the database agent to confirm the query shape.

## Finding the Matching Singles/Shidduchim Subtree

Once you have a candidate `single_id`:

1. **Get the account:** `SELECT account_id FROM singles WHERE id = <single_id>;`
2. **List all singles in that account:** `SELECT * FROM singles WHERE account_id = <account_id>;`
3. **List all shidduchim for that account:** `SELECT * FROM shidduchim WHERE account_id = <account_id>;`
4. **List all references linked to those shidduchim:**
   ```sql
   SELECT rl.*, r.name_en, r.name_he
   FROM reference_links rl
   JOIN references r ON r.id = rl.reference_id
   WHERE rl.shidduchim_id IN (SELECT id FROM shidduchim WHERE account_id = <account_id>);
   ```
5. **List all notes on the matched single:** `SELECT * FROM notes WHERE single_id = <single_id>;`
6. **List all tasks involving the matched single:** `SELECT * FROM tasks WHERE single_id = <single_id>;`

This is the **subtree** that will be affected.

## Exactly What Gets Deleted and What Deliberately Does Not

### DELETE (the requester's own record)

| Table | Rows | Condition |
|-------|------|-----------|
| `singles` | The matched row | `id = <single_id>` |
| `notes` | Notes **on** that single | `single_id = <single_id>` |
| `tasks` | Tasks **assigned to** that single | `single_id = <single_id>` |
| `resumes` | Resumes uploaded for that single | `single_id = <single_id>` |
| `resume_photos` | Photos for that single | `single_id = <single_id>` |
| `entity_files` | Files attached to that single | `target_type = 'single' AND target_id = <single_id>` |

### DO NOT DELETE (family's own data about their own child)

| Table | Rows | Reason |
|-------|------|--------|
| `singles` | Other singles in the same account | They belong to the family, not the requester |
| `notes` | Notes on other singles | Family's private notes about their own children |
| `tasks` | Tasks about other singles | Family's task list |
| `references` | Reference records | A reference is a person in their own right |
| `reference_links` | Links between references and shidduchim | The conversation belongs to both parties |

### PARTIAL / POLICY-DEPENDENT (Story 14.1 published policy)

| Table | What Happens |
|-------|--------------|
| `reference_links` where the **reference** is the requester | The link is removed — the requester's reference record is gone, so the link has no target. |
| `reference_links` where the **reference** is someone else but the **call log** mentions the requester | Story 14.1 policy decides. The call log is also about the person who gave the reference. Some content may remain. |
| `shidduchim` where the requester was the `single_id` | The shidduch row is deleted (it is the requester's pipeline record). |
| `shidduchim` where the requester was the `shadchan_id` | The shadchan is a different person — their shidduchim stay. |

> **UNVERIFIED:** I have not read Story 14.1's published policy document. The exact rule for "which wins" when a reference conversation mentions the requester is not in this runbook. Ask the product owner or read the policy doc before processing the first real request.

## Who to Notify

1. **The requester** (at `contact`): confirmation that their record was removed, or explanation if no match / ambiguous.
2. **The account holder(s)** (account_members of the matched account): notification that a purge request was processed for a single in their account. Do **not** disclose the requester's contact details beyond what they already know.
3. **Any shadchanim** who had active shidduchim with the requester: courtesy notice that the single is no longer in the system.

> **UNVERIFIED:** The notification mechanism (email template? in-app notification? both?) is not built yet. Another agent owns that. Record the notification step manually (log in `purge_requests.notified_accounts` JSONB) until automation exists.

## How to Record the Outcome

Update the `purge_requests` row:

```sql
UPDATE public.purge_requests
SET
  status = 'processed',
  processed_at = now(),
  matched_singles_count = <0 or 1>,
  matched_shidduchim_count = <count of shidduchim deleted>,
  notified_accounts = '["account_id_1", "account_id_2"]'::jsonb,
  result = jsonb_build_object(
    'action', 'deleted' | 'no_match' | 'ambiguous' | 'account_member',
    'single_id', <id or null>,
    'account_id', <id or null>,
    'shidduchim_deleted', <count>,
    'notes_deleted', <count>,
    'tasks_deleted', <count>,
    'references_affected', <count>,
    'notes', '<free text summary of what you did and why>'
  )
WHERE id = <request_id>;
```

## Verification Checklist After Processing

| Check | Method |
|-------|--------|
| Requester's single row gone | `SELECT * FROM singles WHERE id = <single_id>;` returns 0 rows |
| Requester's notes gone | `SELECT * FROM notes WHERE single_id = <single_id>;` returns 0 rows |
| Requester's tasks gone | `SELECT * FROM tasks WHERE single_id = <single_id>;` returns 0 rows |
| Other singles in account intact | `SELECT * FROM singles WHERE account_id = <account_id> AND id <> <single_id>;` returns expected count |
| Reference links to requester gone | `SELECT * FROM reference_links WHERE reference_id IN (SELECT id FROM references WHERE name_en = '<requester_name>');` returns 0 rows |
| Shidduchim where requester was single gone | `SELECT * FROM shidduchim WHERE single_id = <single_id>;` returns 0 rows |
| `purge_requests` row updated | `SELECT * FROM purge_requests WHERE id = <request_id>;` shows `status = 'processed'` |
| Notifications sent (manual log) | `purge_requests.notified_accounts` populated |

## Escalation

| Condition | Escalation Path |
|-----------|-----------------|
| Requester threatens legal action | Product owner → legal counsel |
| Multiple matching singles, requester cannot disambiguate | Product owner → decide whether to build a disambiguation flow |
| Requester is actually an account member (has login) | Redirect to account deletion (Story 14.2) |
| Shidduch involves two singles from different accounts, one requests purge | Product owner → policy decision on cross-account shidduch cleanup |
| Database trigger/function errors during deletion | Database agent (supabase/** owner) |
